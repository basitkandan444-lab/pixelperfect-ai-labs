# OBSIDIAN PRECISION™ — SECTION 1: DESIGN FOUNDATION & SYSTEM PRIMITIVES

**MISSION:** Transform the existing Pixel Perfect Pro frontend into a unified, premium, original design foundation called Obsidian Precision™. This section is strictly design-system work. Preserve all existing functionality and do not modify the enhancement engine, image-processing algorithms, ONNX/GFPGAN/WebGPU/WASM inference, Paddle backend logic, Supabase billing logic, authentication behavior, analytics behavior, or unrelated infrastructure. The purpose is to establish a reusable visual system that every later redesign section can inherit without creating new design debt.

**1.1 FOUNDATION FORENSICS — SMITH + ELLIE:** Audit the complete active frontend surface relevant to the design foundation, including global styles, active routes, shared components, navigation, hero, upload interface, processing interface, result interface, comparison interface, pricing, upgrade UI, dialogs, loading and error states, responsive styles and existing motion patterns. Map hardcoded colors, spacing, typography, borders, radii, elevation, duplicate components, fragmented motion, inconsistent states and visual hierarchy issues. Produce a ranked debt map using LOCATION, CURRENT STATE, USER IMPACT, PRIORITY and RECOMMENDED DIRECTION. Do not modify code during the initial audit.

**1.2 OBSIDIAN PRECISION™ TOKEN SYSTEM — ELLIE + SMITH:** Establish one semantic design source of truth using perceptually coherent `oklch` tokens where appropriate. Define semantic roles for background, foreground, low/mid/high surfaces, borders, strong borders, primary, primary-hover, accent, success, warning, destructive and focus. Establish a responsive typography hierarchy for display, headings, subheadings, body, small text, captions, labels and pricing/numeric content. Establish a coherent spacing scale, a three-tier radius hierarchy and semantic elevation levels. Any hardcoded visual value that remains must have a legitimate contextual reason; do not perform blind global replacement.

**1.3 MOTION FOUNDATION — NOVA + SMITH:** Create centralized duration and easing tokens for fast interaction, standard UI transitions, emphasized transitions, cinematic motion and spring-like interaction where appropriate. All newly created motion must reference the centralized motion system. Do not force unrelated legacy animations into the new system without inspection. Respect reduced-motion preferences and prevent unnecessary visual or performance cost.

**1.4 REUSABLE UI PRIMITIVES — SMITH + MAYA:** Create or improve reusable primitives for buttons, cards, inputs, badges, dialogs, section containers, typography, focus states, loading states and error states. Reuse existing components where practical. Do not create duplicate primitives or unnecessary dependencies. Every primitive must support the new semantic system and provide consistent states across the application.

**1.5 DESIGN CONSISTENCY MIGRATION — SMITH + ATLAS:** Migrate active UI toward the new semantic foundation, prioritizing colors, typography, spacing, borders, radii, elevation, hover states, focus states and transitions. Do not blindly replace `white/10`, `white/5` or similar values because contextual contrast may differ. Inspect each pattern and preserve intentional hierarchy and accessibility.

**1.6 ACCESSIBILITY FOUNDATION — ATLAS:** Verify keyboard navigation, visible focus states, color contrast, touch target sizing, dialog accessibility, interactive state clarity and reduced-motion behavior. Critical accessibility failures block acceptance.

**1.7 PRESERVATION GUARD:** Do not modify enhancement algorithms, image-processing stages, model files, tensor logic, inference paths, Paddle backend logic, Supabase billing implementation or unrelated infrastructure. If a design improvement appears to require modifying a frozen system, document the dependency and defer it to the appropriate later phase.

**1.8 VERIFICATION — ELON:** After implementation, run the project's configured typecheck, build and lint checks, inspect console/runtime errors, verify representative desktop and mobile states, verify responsive behavior, check accessibility and confirm no critical regression. Validate the running application, not only source code. Where appropriate, record before/after visual evidence.

**1.9 INDEPENDENT REVIEW — ALEX:** Independently evaluate visual coherence, hierarchy, typography, spacing, consistency, responsiveness, accessibility, originality and whether the foundation feels like one premium Pixel Perfect Pro system rather than a collection of redesigned components. Do not accept “looks good” as evidence. Classify the result as REJECTED, ITERATING or ACCEPTED. If rejected, identify the concrete weaknesses and return the work through the repair-and-verification cycle.

**1.10 ACCEPTANCE GATE:** Section 1 passes only when one coherent semantic design system exists, active redesigned UI consistently uses it, typography and spacing are coherent, reusable primitives exist, motion is centralized for new work, accessibility states function correctly, responsive behavior is preserved or improved, no critical regression exists, the enhancement engine remains untouched, verification passes, and Alex independently approves the result. If any requirement fails, diagnose the specific failure, correct it, re-test it and review it again before advancing.

**1.11 REQUIRED REPORTING:** After every meaningful milestone, report ACTIVE RESPONSIBILITIES, DISCOVERED, ACTUAL CHANGES, USER IMPACT, VERIFIED, BLOCKERS, DECISION and NEXT ACTION. Only report work that actually happened. Do not fabricate agent activity, evidence, measurements, screenshots or approvals. Do not advance merely because files were edited.

**FINAL PRINCIPLE:** Quality takes priority over speed. The goal is not the largest diff or the most effects. The goal is a stable, coherent, premium foundation that makes every later Pixel Perfect Pro section easier to build, easier to maintain and visibly better for the user.
